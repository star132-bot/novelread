# 任务：个人云端空间 + 管理员平台

交给熟悉整体平台（MKAuth、Mankong Control Plane、服务器运维）的工程师 / Codex。
本文只写需求和约束；服务器地址、凭据位置不在仓库里，执行者使用自己掌握的运维资料。

## 背景

MKread 云书库（`server/`，FastAPI + PostgreSQL，库名 `mkread_library`）目前只有一个**全局书库**：管理员发布 `.mkbook`，所有登录用户同步同一份目录。用户身份来自 MKAuth（书库服务器是 MKAuth 的机密客户端，App 拿书库签发的设备令牌，见 `server/app/auth.py`）。

现有表：`books`、`book_revisions`（全局书库），`device_sessions`、`auth_codes`、`auth_requests`（登录），`voice_packs`（音色包），`app_releases`（应用内更新）。另一个任务正在加 `narration_voices`（服务端管理朗读音色目录），注意合并。

数据库现在只能靠 SSH + psql 管理，用户希望改为在**管理员平台**里查看和管理。

## 需求一：每个用户拥有自己的云端空间（一人一份）

1. **用户表**：首次登录时按 MKAuth `sub` 自动建档（一人只能有一条，`sub` 唯一）。记录显示名、邮箱、角色、状态（正常 / 停用）、配额、创建时间、最近活跃时间。现有 `device_sessions.subject` 关联到这张表。
2. **个人书库**：用户可以把自己的书（`.mkbook`，也可在服务端由 txt/epub 转换）上传到**只属于自己**的空间，只有本人能看到和同步；全局书库保持不变，两者在 App 里分开显示（例如「云书库」和「我的云端」）。
   - 每个用户只有一个空间，按用户配额限制总大小。
   - 校验规则与全局书库一致：复用 `tools/mkbook/mkbook.py` 的 `validate_package`。
   - 同一本书更新时按 `revision` 原地替换，App 侧已有原地更新逻辑（`catalog_id` + `catalog_revision`）。注意：个人书和全局书的 `id` 可能撞车，App 端需要区分来源（例如 catalog_id 加命名空间）。
3. **跨设备同步（建议同期做，可拆分）**：阅读进度、书架文件夹、所选音色保存在用户云端，换手机登录后自动恢复。冲突按「最后修改时间」取胜。
4. **App 端**：「云端书库」页增加「我的云端」：上传本地书、查看已用 / 剩余配额、删除。上传走设备令牌鉴权。大文件注意 Cloudflare 免费版 100 MB 单请求上限（必要时分片上传）。

## 需求二：管理员平台

**位置**：优先作为现有管理平台（Mankong Control Plane，已规划接入 MKAuth SSO）里的「MKread」模块，不另起一个后台。如果判断集成成本过高，再在书库服务上做独立后台，但同样要走 MKAuth 登录，不再依赖共享的 `ADMIN_API_TOKEN`。

**鉴权**：管理员通过 MKAuth 登录，需要具备 `mkread:admin` 角色或在 `ADMIN_SUBJECTS` 白名单中。管理平台调用书库的**管理 API**：在 `server/` 新增 `/api/v1/admin/...`。所有写操作都要记录审计日志（谁、何时、做了什么、改前改后摘要）。

**需要的页面**：

| 模块 | 内容 |
|---|---|
| 概览 | 用户数、7 日活跃、书籍数（全局 / 个人）、存储用量、最近发布、服务健康（`/healthz`） |
| 用户 | 列表（搜索、按活跃 / 注册时间排序）；详情：基本信息、设备与会话（UA、最近使用）、个人书库与配额用量、阅读进度概况；操作：停用 / 启用、吊销全部设备会话、调整配额、设为管理员 |
| 全局书库 | 书籍列表与版本历史、上传 / 下架 / 恢复、查看清单（章节数、字数） |
| 个人书库 | 按用户查看（只读为主），违规内容可下架 |
| 音色 | 音色包（`voice_packs`）状态；朗读音色目录（`narration_voices`，另一任务提供 API）的启用、改名、排序、试听 |
| 应用版本 | `app_releases` 列表、下载次数（如有）、撤回版本、设置最低支持版本（强制更新） |
| 审计日志 | 所有管理操作，可按人 / 时间筛选 |

**不做**：不提供任意 SQL 控制台；不在页面显示令牌、密钥、`.env` 内容；个人书正文默认不在管理端直接展示（隐私），需要时只显示元数据。

## 约束

- 仓库是公开的：不提交服务器地址、凭据、`.env`。
- 只改 MKread 自己的资源（书库服务、`/srv` 下的 MKread 数据目录、数据库 `mkread_library`）。修改管理平台时，遵循那个项目自己的规范，并先备份。
- 数据库结构变更做成可重复执行的迁移；对现有数据（已登录的设备会话、示例书）做兼容。
- App 侧遵守 `AGENTS.md`：Room 结构变更需要迁移和 schema JSON，朗读和阅读必须离线可用。
- 测试：服务端在 `server/tests` 补齐（新表、鉴权、配额、审计）；App 单测和 instrumented 测试保持全绿；在模拟器上端到端验证「上传到我的云端 → 另一台设备登录后同步到」。
- 分支 `feature/narration-cloud` 上还有其他会话在提交，先 `git pull --rebase`，不要强推。

## 交付与验收

1. 新登录用户自动出现在管理平台「用户」列表；同一账号多次登录只有一条用户记录。
2. 用户 A 上传的书只有 A 能同步到；B 看不到，管理员能看到元数据。
3. 超出配额时上传被拒绝，并给出明确提示。
4. 管理员在平台上停用用户后，该用户的设备令牌立即失效，App 提示重新登录。
5. 全局书库上传 / 下架、App 版本撤回、音色启用与排序都能在平台完成，且有审计记录。
6. 文档更新到 `docs/cloud-library.md`（公开部分）；运维细节写在执行者自己的私有运维资料里。

## 需要先和用户确认的点

- 「每个用户只能有一个自己的云端」是否就是上面的「个人书库 + 同步」，还是还包括其他东西（例如个人笔记、书签）。
- 默认配额多大（例如 1 GB）？是否允许上传 txt/epub，由服务端转换为 MKBook？
- 管理平台放在 Mankong Control Plane 里是否合适。
